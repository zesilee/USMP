# 任务：.claude 项目配置自优化审计与重构

## 目标
完整扫描本项目的 AI 工作配置资产，识别冗余、过期、冲突、僵化、低价值、重复的规则；输出优化方案，经用户逐条确认后执行重构瘦身。
**本次只优化 AI 工作配置文件，严禁改动业务源代码。**

## 扫描范围（按本仓库实际布局）

| 资产 | 路径 |
|------|------|
| 斜杠命令 | `.claude/commands/**/*.md` |
| 技能 | `.claude/skills/*/`（每个技能读其 SKILL.md 及附属文件） |
| 子代理 | `.claude/agents/*.md` |
| Hooks 配置 | `.claude/settings.json` 的 `hooks` 块 + `.claude/hooks/*.sh` 脚本 |
| 设置 | `.claude/settings.json`、`.claude/settings.local.json` |
| 项目规范 | 根目录 `CLAUDE.md`（注意：§2 红线享有特殊保护，见下） |
| 附属文档 | `.claude/HOOKS.md` |
| Spec 规范 | `openspec/specs/**/*.md`、`openspec/SPEC_CONVENTIONS.md`（只审"作为规则的约束"，不审业务能力描述） |

**范围外（只读交叉引用，禁止修改）**：`docs/memory/`（知识资产非规则）、`.githooks/`（git 门禁层，与 CI 镜像联动，改动须单独立项）、`openspec/changes/` 与 `openspec/tasks/`（工作产物非配置）、业务源代码。

## 评估判定标准：命中即标记待优化
1. 过期工作流约束：强制分步流程、必须先输出变更清单再改代码、过度前置检查，且已被更新的流程（如 §5 opsx 工作流）取代。
2. 重复规则：多份文件里存在完全相同或高度重叠的编码、注释、架构约束（例如 CLAUDE.md 与某 skill 各写一遍同一约束）。
3. 僵尸技能：定义了工作流但无证据表明仍在使用，且其目标已被其他机制覆盖。
4. 废弃斜杠命令：功能已被原生能力或其他命令替代。
5. 冲突约束：两份规则给出互相矛盾的要求。
6. 过度约束：硬性强制规则收益很低，但显著降低灵活性、造成机械僵硬输出。
7. 临时一次性任务留下的规则，任务早已完成却永久留存。
8. hooks 脚本：不再有实际防护价值，或其 matcher 永远不会命中。

### 使用现状的证据规则（防瞎猜）
AI **拿不到会话调用历史**，禁止凭空断言"近 N 次任务未被触发"。判断使用现状只允许基于可验证证据：
- `git log --follow -- <文件>` 的最后实质性修改时间与修改频率
- CLAUDE.md §7 技能映射表是否还引用它（被映射表引用的技能不得判僵尸）
- 其他配置/文档对它的交叉引用（grep 全仓库）
- hooks 脚本的日志文件（如 `.claude/hooks/*.log`）
- 内容本身引用的路径/命令/技术栈是否已在仓库中消失（最强证据：引用了已删除的东西）

证据不足时，结论只能标 **「低置信度，需人工确认」**，建议动作最高只能到「休眠」，禁止直接建议「删除」。

## 高价值资产 → 保留（可精简文字，但不能删除）
1. 项目架构知识、模块边界说明
2. 项目专属术语词典
3. 技术栈版本、第三方依赖、基础设施约定
4. 编码风格、注释规范（建议类而非强制枷锁）
5. 高危操作安全护栏

### 红线保护（不可协商）
根目录 CLAUDE.md **§2 架构红线（R01–R18）、§6.5 安全红线（W01–W07）、TDD 军规（T01–T09）** 及 hooks/CI 双层拦截体系，是刻意设置的硬门禁：
- **禁止建议「降级为参考建议」或「删除」**，只允许建议「精简措辞」（保持约束力不变）。
- 涉及它们的任何条目一律标 **高风险**，即使用户批准也要在执行前再次显式复述影响并二次确认。

## 优化手段优先级（温和 → 激进）
1. **降级**：强制约束 → 参考建议。在条目处标注「⚠️ 仅作为参考建议，非硬性强制，可根据任务灵活决策」。（红线类禁用本手段）
2. **精简**：删除冗长重复文字，保留核心意图，压缩篇幅。
3. **合并**：将多处重复规则合并到单一权威位置，其余位置改为一行引用（如「详见 CLAUDE.md §x」），删除重复正文。
4. **休眠（安全首选）**：对 skill/command 不删除文件，在 frontmatter 添加 `disable-model-invocation: true`，禁止自动触发，仅可手动 `/命令` 按需启用。
5. **删除**：真正僵尸、过期、无任何价值的文件。仅限有强证据（见证据规则）的条目。

## 执行流程（五步闭环）
**Step 1. 全量扫描**：按上表读取所有配置文件完整内容。文件多时可用子代理并行分片扫描，但汇总判断在主上下文完成。

**Step 2. 输出审计报告**：写入 `docs/reviews/self-audit-<日期>.md`（同时在对话中给摘要），表格列出每一项资产，**逐条编号**：
- 编号（供审批引用）
- 文件路径
- 当前功能简介（一句话）
- 使用现状评估（活跃 / 低频 / 僵尸 / 冲突 / 冗余）+ **证据**（引用哪条 git 记录、哪处交叉引用；无证据则标「低置信度」）
- 建议优化动作：【降级 / 精简 / 合并 / 休眠 / 删除 / 原样保留】
- 风险等级：低 / 中 / 高，说明修改后潜在影响

**Step 3. 暂停审批**：等待用户逐条确认（可回复「执行 1,3,5」「除 4 外全部执行」等），**没有明确指令绝对不修改任何文件**。含「删除」或「高风险」条目的，须用户对该条目明确点头，不接受笼统的「都行」。

**Step 4. 执行变更**：仅执行获批条目。执行后自检：
- `.claude/settings.json` / `settings.local.json` 通过 JSON 语法校验（`python3 -m json.tool` 或 `jq .`）
- settings.json hooks 块引用的每个脚本仍存在且可执行
- 被合并/删除的文件在全仓库无残留引用（grep 校验）
- 被保留文件的 frontmatter 仍合法

**Step 5. 输出《优化结果汇总》**：列出所有变更（含跳过项及原因），附 `git diff --stat` 与关键 diff 片段。然后做一次冲突自检：检查剩余规则之间是否还存在矛盾，如有则给出二次调整方案（同样需审批后执行）。

### 提交规则
变更提交遵守项目自身门禁（R13 禁直接 push main）：在独立分支上以 `docs:` / `chore:` 提交（What/Why/How 三段式），走 PR 合入；或应用户要求仅留在工作区不提交。

## 优化后预期效果
- 去掉僵化强制工作流，保留项目上下文知识
- 减少重复约束，单一权威来源 + 引用
- 规则清晰、轻量、低冗余
- 既不过度锁死 Agent 行为，又不丢失项目关键约定与安全护栏
